ng-form-saver — four views

An Angular library that keeps a form's in-progress state alive across reloads and navigation. Two moving parts do the work; everything else is options plumbing. These four zoom levels go from who touches the system down to the two code paths that define it.

1Context

Who touches the librarysystem boundary: the ng-form-saver package

The library never talks to a network of its own. Its only outward dependencies are a storage backend and — optionally — the Angular Router, which it reads a URL from when autoKey is on. Everything else it receives by injection from the host application.

3Components

Two components and an options tokeninside projects/ng-form-saver/src/lib

The directive is a thin adapter: it finds the form's AbstractControl, merges options, and hands both to the service. The service holds all the behaviour — key resolution, storage resolution, restore, migration, debounced save. The injection token is the only shared state between them.

4Code

The restore path and the save patheverything the service does, in two directions

Restore runs once, synchronously inside attach() — unless the backend returns a Promise, in which case it resolves later and its errors are swallowed. Save runs on every debounced value change. There is deliberately no startWith, so an untouched restored form writes nothing back.

Level 4 · rules worth knowing
ConcernBehaviour
keyopts.key → else form:<router.url> when autoKey and a Router exists → else the literal 'form-saver', shared by every unkeyed form.
storage'localStorage' / 'sessionStorage' strings, or a custom object. Every miss ends at a fresh in-memory Map — getStorage() allocates one per call.
payload{ v, data, meta, expiresAt? }. meta is a flat map of dotted paths to { dirty, touched }, with $root for the top control.
migrationsForward only. Walks from === current and applies migrate(data) until it reaches version, breaking on a missing link, capped at 50 hops. Mutates the parsed payload in place.
ttlexpiresAt = Date.now() + ttl stamped on each save. On restore, an expired payload is cleared and skipped.
asyncA Promise from getItem defers restore; the rejection handler is empty. Promise results from setItem/removeItem are also swallowed.
failure modeQuota errors, serialization errors, and malformed JSON all resolve to "do nothing". Saving is best-effort by design, and silent.
teardownhandle.destroy() unsubscribes but leaves stored data. Only clear() or clearOnSubmit removes it.
·Gaps

What the model exposesobservations from mapping, worth a decision

  1. Failing test
    app.spec.ts asserts an <h1> that no longer exists.
    The spec expects Hello, form-saver, but app.html is just <router-outlet />. Both CI and the release workflow gate on npm test, so publishing is blocked by a stale demo test.
  2. Wrong store
    The demo writes to sessionStorage but reads and clears localStorage.
    formOptions sets storage: 'sessionStorage', while readSaved() reads localStorage directly and clearSaved() calls saver.clear(key) with no storage argument — which resolves to localStorage. The payload preview and the TTL readout will stay empty.
  3. API shape
    clear(key) without a storage argument cannot reach a custom backend.
    It re-resolves storage, so for a custom or fallback backend it clears a different store than the one attach() wrote to. Callers holding an AttachHandle should use handle.clear(); the service-level overload is a trap worth documenting or removing.
  4. Coverage
    CI never runs the library's own test target.
    npm test resolves to the root form-saver project (root: ""), so projects/ng-form-saver's karma target is skipped. The engine at Level 3 — key resolution, TTL, migrations, meta walking — has no tests at all.
  5. Deprecated
    ENVIRONMENT_INITIALIZER is deprecated in Angular ≥19.
    It also does nothing here beyond injecting the token. Either drop it or move to provideEnvironmentInitializer() before the next major.
  6. Default key
    Unkeyed forms all share the key 'form-saver'.
    Two forms with no key and no autoKey overwrite each other's drafts, and each will patch the other's values on attach.
  7. Dead code
    NgFormSaver and its spec are leftover scaffolding.
    Not exported from public-api.ts, not used by the demo. It exists only so a generated spec has something to instantiate.
  8. Version skew
    Root package.json is 1.3.0, the library is 1.3.1.
    Only the library version reaches npm, so this is cosmetic — but the root version is what a reader checks first.
  9. Untested path
    Nothing in the repo installs the built package.
    The demo imports source by relative path, so export gaps in public-api.ts, packaging metadata, and typings would only surface after publishing. A smoke test against dist/ng-form-saver would close the loop that Level 2 leaves open.
Levels follow Simon Brown's C4: context, containers, components, code. Read from the working tree at commit 4d427ee — 44 tracked files, no dist committed. Level 4 is scoped to FormSaverService, the only place non-trivial logic lives.
